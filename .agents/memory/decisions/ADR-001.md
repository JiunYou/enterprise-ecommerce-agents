# ADR-001: Architecture Style Decision

## Metadata
- **ADR ID:** ADR-001
- **Status:** Proposed
- **Owner Agent:** System Architect Agent
- **Created Date:** 2026-08-24
- **Related ADR:** ADR-Phase1-001, ADR-Phase2-001

## Context
本專案 (Enterprise E-Commerce Platform) 經歷了 Business Domain Analysis (Phase 1) 與 DDD Strategic Design (Phase 2)，已確立 7 個 Bounded Context (Catalog, Order, Cart, Inventory, Payment, Marketing, Identity)。根據先前的專案規劃，技術雷達涵蓋了 ASP.NET Core 與 Node.js 雙重技術堆疊。現在我們必須確立系統的宏觀架構風格 (Architecture Style)，作為後續系統拆分、團隊編制與基礎設施部署的最高指導原則。

## Problem
如何在初期保證交付速度與交易強一致性的同時，又保留系統未來針對特定 Bounded Context 獨立擴容、技術異質性（支援 .NET 與 Node.js），以及適合 AI Agent 切入開發的架構彈性？

## Options
- **Option A:** Modular Monolith (純單體模組化架構)
- **Option B:** Microservices (純微服務架構)
- **Option C:** Hybrid Architecture (混合式架構：核心 Modular Monolith + 外圍 Independent Services)

## Decision
我們選擇 **Option C: Hybrid Architecture** 作為 Enterprise E-Commerce Platform 的架構風格。

我們將把需要強交易一致性的核心領域（Order, Inventory, Payment, Identity）以 **ASP.NET Core Modular Monolith** 進行實作；而將需要處理高併發讀寫、整合外部系統或需要快速試錯的外圍與輔助領域（Cart, Catalog Search, Marketing, API Gateway, 報表等）以獨立的 **Node.js Services** 進行實作。

## Consequences

### Positive Consequences
- **核心穩定與快速交付：** 複雜的訂單狀態流轉與庫存事務集中於單體內部，免去初期分散式交易 (Saga/2PC) 的複雜度，提升初期交付速度。
- **局部彈性擴展：** 購物車與商品搜尋可隨大促銷活動獨立擴展 Node.js 節點，不影響核心訂單系統的運作。
- **AI Agent 與團隊協作友好：** 架構允許 AI Agent 或新團隊輕易接手單一明確的 Node.js 獨立服務，而不必牽涉或破壞龐大的核心系統，確保 Security 與 Permission Boundary 更加清晰。

### Negative Consequences
- **通訊複雜度提升：** 跨越 Monolith 與獨立 Services 之間必須制定明確的通訊協定 (REST, gRPC) 以及非同步事件流 (Event Bus / Message Queue)，這增加了架構整合負擔。
- **部署雙軌制：** 需同時維護 .NET 單體的部署管道與多個 Node.js 服務的容器化 CI/CD 流程，增加了 DevOps 的初期建置成本。

## Future Considerations
本架構保持了高度的可演進性 (Long Term Evolution)。當 Modular Monolith 內部的某個模組（例如：Inventory Domain）成長到特定規模、遇到資料庫擴展瓶頸，或交由專職團隊維護時，可依據原本就已遵守的 DDD Bounded Context 邊界，順暢地將其抽離成為另一個獨立的 Microservice，平滑過渡至完整的微服務架構。
